ACID Transaction Principles in GeoResQ-Sync

In disaster relief, sending duplicate aid or recording aid when warehouse stock is zero can lead to lost lives. We implement strict ACID guarantees:

A - Atomicity
Both stock deduction and dispatch audit log succeed together, or everything is rolled back completely.
C - Consistency
Protected by SQL CHECK constraint (quantity >= 0) and foreign key cascades.
I - Isolation
Pessimistic row-level locking (SELECT ... FOR UPDATE) blocks concurrent race conditions.
D - Durability
InnoDB write-ahead redo log ensures committed dispatches survive sudden power outages.
Q1: Why MySQL 8.0 Spatial GIS instead of calculating distance in JavaScript?
JavaScript array loops scale at O(N) in Node.js server memory. MySQL 8.0 uses R-Tree SPATIAL INDEX and performs ST_Distance_Sphere directly in C++ at the database engine layer in under 2ms for thousands of points.
Q2: How does pessimistic locking prevent stock deficits during disaster panic?
By executing SELECT quantity FROM relief_inventory WHERE id = ? FOR UPDATE, MySQL places an exclusive row-level lock. If 10 volunteer teams request aid simultaneously, transactions are serialized. If remaining stock is insufficient, the transaction issues ROLLBACK.
Q3: How do database triggers maintain state synchronization?
When a volunteer's assigned_rescue_id is updated, trg_auto_update_sos_on_volunteer_assign fires automatically to mark the SOS request as ASSIGNED. When a donor's contribution is approved, trg_increase_inventory_on_donation_approved automatically increments warehouse stock.
